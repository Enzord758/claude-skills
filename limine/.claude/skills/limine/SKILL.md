# Limine bootloader (this machine)

CachyOS/Arch, UEFI, Btrfs root on `/dev/sda3` (subvol `@`), ESP on `/dev/sda1` mounted at `/boot`. Kernel: `linux-cachyos`. Dual-boot with Windows 11 on the same ESP. Secure Boot is **on** with the user's own sbctl keys (+ Microsoft vendor keys).

## The one rule: limine.conf is sealed

`ENABLE_ENROLL_LIMINE_CONFIG=yes` means the BLAKE2B hash of `/boot/limine.conf` is baked into `/boot/EFI/limine/limine_x64.efi`, which is then re-signed with sbctl. Because Secure Boot is active *and* a hash is enrolled, Limine enforces strict mode on every boot:

- If `limine.conf` doesn't match the enrolled hash → **panic, machine won't boot.**
- Every kernel/initramfs path must carry a correct `#<b2sum>` suffix → otherwise panic.
- Wallpaper/font paths with a missing or wrong hash are silently skipped (fallback to plain background) — annoying but not fatal.
- The boot-menu editor is disabled, so the user cannot fix a cmdline at boot time.

So: any byte changed in `limine.conf` by hand must be followed by `limine-enroll-config` (re-enrolls the hash **and** re-signs the EFI binary). The regeneration tools (`limine-update`, `limine-entry-tool`, `limine-snapper-sync`) already do this via `/etc/boot/hooks/post.d/90-limine-enroll-config`, so after running one of those no extra step is needed.

Snapper takes timeline snapshots hourly and `limine-snapper-sync` rewrites `limine.conf` each time, so the file can change between your read and your write. All limine tools serialize on `/run/lock/boot-partition.lock`; `limine-enroll-config` does not take it itself, so wrap a hand edit and its enroll in that lock:

```bash
cp -a /boot/limine.conf /boot/limine.conf.claude-bak
flock --timeout=60 /run/lock/boot-partition.lock sh -c '
  sed -i "1,/^\/[^\/]/{s/^timeout:.*/timeout: 3/}" /boot/limine.conf &&
  limine-enroll-config'
```

Restrict `sed` to the header (`1,/^\/[^\/]/`) so it can never touch the ~1700 lines of generated entries below.

## Who owns what

Edit the *source*, not the generated output, whenever a source exists. Hand edits to generated blocks get overwritten on the next kernel update or snapshot.

| What | Source of truth | Regenerate with |
|---|---|---|
| Global menu options at the top of `limine.conf` (`timeout`, `default_entry`, `wallpaper`, `term_*`, `interface_*`…) | Hand-written in `/boot/limine.conf` above the first `/` entry; tools preserve them | `limine-enroll-config` after editing |
| Kernel entry (`/+Arch Linux` → `//linux-cachyos`) | Generated by `limine-entry-tool` | `limine-update` (full) or `limine-entry-tool` |
| Kernel cmdline | `/etc/kernel/cmdline` (used because `KERNEL_CMDLINE[...]` is unset in `/etc/default/limine`) | `limine-update` |
| Snapshots submenu (`//Snapshots`, `///894 │ …`) | Generated by `limine-snapper-sync` from snapper | `limine-snapper-sync` |
| `/+Windows` | Generated (Windows detection is independent of `FIND_BOOTLOADERS`) | `limine-entry-tool` / `limine-update` |
| (no `/EFI fallback`) | Removed 2026-09-27: `/EFI/BOOT/BOOTX64.EFI` is a signed copy of **Windows bootmgr**, so the entry duplicated Windows. `FIND_BOOTLOADERS=no` in `/etc/default/limine` keeps it from being re-added (setting it doesn't delete an existing block — that was removed by hand) | — |
| Tool settings (boot order, verification, sort, UKI, enroll) | `/etc/default/limine` | — (read by all limine tools) |
| Snapshot-sync settings | `/etc/limine-snapper-sync.conf` (package defaults) overridden by `/etc/default/limine` (`SNAPSHOT_FORMAT_CHOICE=8`: `date│description`) | `limine-snapper-sync` |
| initramfs contents | `/etc/mkinitcpio.conf` — `kms` hook deliberately removed (it pulled nouveau + ~100 MB firmware; nvidia modules in `MODULES` give early KMS). Don't re-add it | `limine-update` |

Config precedence for the tools, lowest → highest: `/etc/limine-entry-tool.conf` (package-owned) → `/etc/limine-entry-tool.d/*.conf` → `/etc/default/limine` (not package-owned, overrides everything, also read by limine-snapper-sync). New tool settings belong in `/etc/default/limine` so pacman upgrades never produce a `.pacnew` conflict. Existing snapper-sync settings live in `/etc/limine-snapper-sync.conf`; editing them there is fine, but prefer `/etc/default/limine` for new ones and mention the choice.

The kernel cmdline in the snapshot entries is copied at snapshot time — changing `/etc/kernel/cmdline` only affects the main kernel entry (and future snapshots). That's intended: snapshots should boot the way the system was.

## Workflow: inspect → propose → wait → apply → verify

The user wants to see changes before anything touches `/boot`. This session runs as root, so nothing stops a command from executing — the pause has to come from you.

1. **Inspect** with read-only commands (below). Read the actual current values; don't assume they match this document.
2. **Propose**: show the exact diff for each file, plus the exact commands you'll run, in order. Say what each command does and which one makes it "take effect". Mention any risk (e.g. "if this cmdline param is wrong the kernel still boots, you can pick an older snapshot").
   For anything that changes how the menu looks (wallpaper, colours, timeout, default entry, branding), write the proposed `limine.conf` to a scratch copy and render it: `python3 ~/.claude/skills/limine/scripts/render-menu.py -c <copy> -o <png> [--wallpaper <new image>]`, then Read the PNG and show it. Render the current config too when a before/after helps. The preview is approximate (TTF font instead of Limine's bitmap font, tree glyphs), but colours, transparency, margins, text and entry order are right — say so if the user asks how exact it is.
3. **Wait for an explicit OK.** Don't run state-changing commands in the same turn as the proposal.
4. **Apply**: back up first (`cp -a /boot/limine.conf /boot/limine.conf.claude-bak` and the same for any `/etc` file), then edit, then run the regeneration command(s).
5. **Verify** with `bash ~/.claude/skills/limine/scripts/limine-check.sh`. It confirms the enrolled hash matches, the EFI binary is signed, every file hash in the config is correct, and shows the effective cmdline/boot order and snapshot/ESP state. Report the result honestly; if anything is red, stop and explain before doing more.

**Talking to the user.** The user prefers short, plain answers over exhaustive technical ones — in review they found the thorough-but-dense replies harder to follow. Lead with what's going on and what you propose, then the commands. Keep internals (hash slots, hook order, byte offsets, why a tool behaves as it does) out of the reply unless they change what the user should do; they belong in your own reasoning. Write in the user's language (usually Danish).

For pure questions ("what's my timeout?", "what does my boot menu look like?") start with `limine-check.sh` — it answers most of them in one read-only call — and skip the proposal ceremony.

## Commands: safe vs. state-changing

**Assume every `limine-*` command writes to `/boot` until proven otherwise.** Two traps, both hit while writing this skill:
- The wrapper scripts don't implement `--help`; unknown flags are ignored and the tool runs for real. `limine-update --help` did a full initramfs rebuild + config rewrite + enroll + sign.
- `limine-entry-tool` runs the pre/post boot hooks (reset enrollment → re-enroll → re-sign the EFI binary) for *every* action except `--help`, `--version` and `--get-cmdline` — even for display-only actions like `--tree`. Add `--no-hooks` to any other inspection call.

To learn what a tool does, read its source (`/usr/bin/limine-*` are bash wrappers; shared logic in `/usr/lib/limine/limine-common-functions`), `man limine`, or `/usr/share/doc/limine/`.

Read-only (safe to run anytime):
- `bash ~/.claude/skills/limine/scripts/limine-check.sh` — full health check
- `limine-list` (= `limine-entry-tool --no-hooks --tree`) — menu tree as Limine will show it
- `limine-snapper-list`, `limine-snapper-info` — snapshot entries (both run with `--no-hooks`)
- `python3 ~/.claude/skills/limine/scripts/render-menu.py [-c conf] [-o png] [--expand Snapshots] [--interrupted]` — PNG preview of the boot menu at the real 3840×2160 boot resolution (reads only; `--interrupted` = state after a keypress)
- `limine-entry-tool --get-cmdline linux-cachyos` — effective cmdline (one argument; adding a profile name gives "Invalid arguments")
- `limine-entry-tool --version`, `limine --version`, `sbctl status`, `sbctl verify`, `efibootmgr [-v]`, `bootctl status`
- Snapshots: don't run `snapper list` (with or without `--no-dbus`) — with ~900 snapshots it takes minutes and looks hung. Use `ls /.snapshots | wc -l` for the count, `/.snapshots/<N>/info.xml` for one snapshot's date/description, and `limine-snapper-list` for what's in the menu
- `grep -vE '^\s*(#|$)' /etc/default/limine` — active settings (the file is mostly comments)
- Reading `/boot/limine.conf`: it's ~1700 lines, almost all snapshot entries. Read the top with `sed -n '1,/^\/+/p'` and list entries with `grep -nE '^\s*/+[^/]' /boot/limine.conf | grep -v '///'`.

State-changing (only after the user's OK):
- `limine-enroll-config` — re-hash `limine.conf` into the EFI binary + `sbctl sign`. Cheap; run after any hand edit to `limine.conf`.
- `limine-entry-tool` — regenerate OS/kernel/EFI entries (+ enroll via hook). `--scan` (or `limine-scan`) re-detects Windows/other EFI loaders. `--add-efi <name> <path> [--priority N]` adds a custom EFI entry.
- `limine-update` — `limine-install --no-efi-register` + rebuild initramfs + regenerate entries + enroll + sign. Use after changing `/etc/kernel/cmdline`, mkinitcpio config, or Limine tool settings. Takes ~30 s.
- `limine-snapper-sync` — rebuild the Snapshots submenu (+ enroll).
- `sbctl sign -s <file>` — sign and remember a file for future re-signing.
- `efibootmgr -o …` / `-n …` — firmware boot order / one-shot next boot.

## Recipes

**Boot menu appearance** — global options at the top of `limine.conf`. Full list with exact semantics: `/usr/share/doc/limine/CONFIG.md` (version-matched to the installed Limine; check it rather than relying on memory, option names changed between major versions). Backed up in `~/dotfiles/system/limine/` (header, `wall.png`, `/etc/default/limine`, `restore.sh`) — after changing the header or `/etc/default/limine`, offer to refresh those copies (`awk 'BEGIN{h=1} /^\/[^\/]/{h=0} h' /boot/limine.conf > …/limine-header.conf`); the user commits. Current setup (2026-09-27): Tokyo Night (night) palette in `term_palette`/`term_palette_bright`/`term_*`, semi-transparent `term_background: a01a1b26`, accents `interface_branding_colour: 7aa2f7`, `interface_help_colour: bb9af7`, `interface_help_colour_bright: 7dcfff`; wallpaper `boot():/wall.png#<b2sum>`. Previously Catppuccin Mocha. Read the live header rather than trusting this line.
- Colours are `RRGGBB` hex without `#`; `term_palette` is 8 `;`-separated colours (black, red, green, brown/yellow, blue, magenta, cyan, gray), `term_background`/`term_foreground` single colours; background accepts `AARRGGBB` for transparency over the wallpaper.
- New wallpaper: copy the image to `/boot/` under a new name (FAT32, keep it small — BMP/PNG/JPEG/QOI; keep the old file for rollback), compute `b2sum` of the *copied* file, write `wallpaper: boot():/<file>#<hash>`. Forgetting the hash makes the wallpaper silently disappear. Check the image's size (`file <img>`): the default `wallpaper_style` is `stretched`, so anything far from the monitors' 16:9 (2560×1440 / 3840×2160) distorts — suggest `wallpaper_style: centered` + `backdrop: 1a1b26` (matches the palette). If the chosen file looks like a random screenshot, say so and ask. Multiple `wallpaper:` lines = random pick.
- `term_background` is `TTRRGGBB` where `TT` is *transparency* (00 = opaque; a 6-digit value is opaque). The current `1e1e2e` hides the wallpaper entirely except the 64 px margin — and `wall.png` is mostly black with the artwork on the left, so right now it's effectively invisible. `a01e1e2e` lets it show through clearly; preview with `render-menu.py` before proposing. For full transparency use `ff1e1e2e`, not `ffffffff` (seen in some themes): the selected entry is drawn in reverse video with the background colour as text colour, so a white background RGB makes the highlighted name unreadable.
- Then `limine-enroll-config`.

**Timeout / default entry** — `timeout: N` (0 = boot instantly without the menu, `no` = wait forever). `default_entry` can be a 1-based index counting every visible entry in the menu tree, or — more robustly — a path like `Arch Linux/linux-cachyos` or `Windows/Windows 11`. Prefer the path form: indices shift when entries are added or expanded (this machine uses `Arch Linux/linux-cachyos`). `remember_last_entry: yes` overrides `default_entry`. For "boot Windows once", suggest `efibootmgr -n 0000` (firmware one-shot) or `systemctl reboot --boot-loader-entry=…` if supported, instead of editing the config.

**Kernel parameters** — edit `/etc/kernel/cmdline` (single line, the full cmdline incl. `root=UUID=… rootflags=subvol=@ rw`), then `limine-update`. Don't edit the `cmdline:` line in `limine.conf` — it gets regenerated. Verify with `limine-entry-tool --get-cmdline linux-cachyos` and, after the next boot, `cat /proc/cmdline`. The existing `video=`, `pcie_*`, `nvidia_drm.modeset=1`, `lsm=…` params are deliberate (see `~/dotfiles/Installation-Instructions.md`); don't drop them while editing. If the user wants the change reproducible after reinstall, also offer to update that notes file.

**Snapshot entries / full ESP** — settings in `/etc/limine-snapper-sync.conf` (`LIMIT_USAGE_PERCENT=85` caps `/boot` usage, `SNAPSHOT_FORMAT_CHOICE=2`, `EXCLUDE_SNAPSHOT_ENTRIES`, `RESTORE_METHOD=replace`), overridable in `/etc/default/limine`. Apply with `limine-snapper-sync`.
- How many snapshots exist is snapper's job (`/etc/snapper/configs/root`: `TIMELINE_LIMIT_*`, `NUMBER_LIMIT`), not Limine's — the menu mirrors snapper, capped by `LIMIT_USAGE_PERCENT`. If the snapshot count is far above what those limits allow, the pruning isn't running: check `systemctl is-enabled snapper-cleanup.timer` (timeline *creation* and *cleanup* are separate timers). Fixing snapper is the real fix; Limine follows on the next sync.
- ESP space: each distinct kernel+initramfs a snapshot needs is kept once, deduplicated by hash, in `/boot/<machine-id>/limine_history/` (~220 MB per initramfs). Space is freed when the snapshots referencing a version disappear and `limine-snapper-sync` runs. Never delete files in `limine_history/` by hand — entries pointing at them would panic under Secure Boot. `limine-snapper-remove` removes snapshot entries properly. Inspect with `limine-snapper-list` / `limine-snapper-info`; `limine-snapper-restore` is an interactive rollback — let the user run it themselves.

**Windows / other EFI entries / menu order** — `BOOT_ORDER="*, *fallback, Snapshots"` in `/etc/default/limine` orders entries; Windows has `order-priority=20`, Arch `50`. Windows chainloads `boot():/EFI/Microsoft/Boot/bootmgfw.efi` under firmware Secure Boot verification (needs no hash). If Windows vanished from the menu, `limine-entry-tool --scan` (untested whether `--scan` re-adds EFI fallback despite `FIND_BOOTLOADERS=no` — check `limine-list` afterwards). Windows updates sometimes reset firmware boot order: check `efibootmgr -v` for `BootOrder`/`BootNext` — the entry whose path is `\EFI\limine\limine_x64.efi` (currently `0002`) should be first. Select it by path rather than hard-coding the number, since entries can be recreated. Mainboard is an ASUS ROG STRIX X670E-F (AMI): **F8** = one-time boot menu, **Del** = setup.

Firmware entries on this machine: `Boot0002 "Limine"` → `limine_x64.efi` (current Limine, config hash enrolled, strict mode). `Boot0001 "Limine Boot Loader"` → `\EFI\limine\BOOTX64.EFI`: an old Limine 12.3.3 from install, signed with the sbctl keys but with **no** enrolled hash — so it boots even when `limine.conf` doesn't match (see recovery below). Keep it; don't "clean it up" without mentioning that role. `Boot0000` Windows Boot Manager.

## If it won't boot

The user may be writing from a phone with the machine stuck, so give short numbered steps they can follow at the firmware screen, least invasive first:
1. **"CHECKSUM MISMATCH FOR CONFIG FILE"** (someone edited `limine.conf` without enrolling): power on, press **F8**, pick **"Limine Boot Loader"** (Boot0001, the old un-enrolled binary). It ignores the enrolled hash, and its config editor works. Boot `linux-cachyos` normally, then run `limine-enroll-config` (after a quick `limine-check.sh` to confirm the rest of the config is sane). Reboot normally. Caveat: this binary is 12.3.3, so very new config options may be ignored; kernel/initramfs hash mismatches still panic in it by default.
2. If that entry is gone or also fails: **Del** → firmware setup → temporarily disable Secure Boot. Without active Secure Boot Limine drops strict mode. Boot, `limine-enroll-config` (or restore `/boot/limine.conf.old` / `.claude-bak` first), then re-enable Secure Boot — and remind them, since forgetting leaves the machine unprotected.
- The Limine menu editor can't be used to fix things in strict mode — it's disabled there, so don't suggest it for the main entry. Windows stays bootable via F8 → Windows Boot Manager throughout.
3. **Bad kernel param / broken kernel** (menu shows, kernel fails): pick a snapshot from the Snapshots submenu — it boots a read-only snapshot with its own kernel copy from `limine_history/`; `limine-snapper-restore` can then roll back.
4. Last resort: CachyOS/Arch live USB (Secure Boot off), mount `/dev/sda3` subvol `@` and `/dev/sda1` on `/boot`, `arch-chroot`, fix, `limine-update`.

`/boot/EFI/limine/limine_x64.bak` is the pristine (un-enrolled) binary the tools restore from before each enroll; don't delete it.
